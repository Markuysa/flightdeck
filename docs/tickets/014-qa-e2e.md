Prove the top-level acceptance criteria (PRD §6) end to end against a fixture project,
with dispatch and merge mocked at the boundary.

## Likely files
- `internal/e2e/{e2e_test.go,fixtures}` (or `ui/e2e/` if driven through the built UI)

## Acceptance criteria
- [ ] Boots the server against a fixture repo with tickets in every status and asserts the
      board derives each one correctly over the real HTTP API.
- [ ] Asserts a lying `status: ready` on a blocked ticket still renders blocked (the
      ADR-001 guarantee) through the full stack, not just the derive unit test.
- [ ] Dispatch is disabled for a non-ready ticket and, when fired, calls the (stubbed)
      routine endpoint with the right payload; approve merges only the named PR via a
      stubbed GitHub.
- [ ] Asserts no token-shaped string is ever sent to the client across the covered flows.
- [ ] Deterministic — fixtures and stubs only, no live services. Runs in CI.

## Handoff
List which PRD §6 criteria are covered by an automated test and which remain manual.

## Handoff

`internal/e2e` boots the real `api.Server` behind `httptest` and drives it over real HTTP
(bearer → session cookie), keeping `git` + `derive.Derive` real and stubbing only the
routine/GitHub boundary. It runs under the existing CI `go test -race ./...` — no browser or
extra infra. Seams used: real `registry.Store` (temp file); real `api.NewGitHubSource` against a
no-remote fixture for pure git+derive; a custom `stubbedGitHubSource` (real git+derive + canned
PRs) where PR/CI state or approve is needed; a `stubDispatcher` recording Fire/ApproveMerge.

**PRD §6 coverage — automated here:**

| PRD §6 criterion | Covered by |
|---|---|
| Register a repo → tickets appear with correct derived statuses (fixture, known git state) | `TestBoardDerivesEveryStatusOverRealHTTP` |
| merged→`done`, open PR→`in_review`+live CI, unmet dep→`blocked`; never a stored field | `TestBoardDerivesEveryStatusOverRealHTTP`, `TestBoardAnnotatesInReviewTicketWithPRAndCIStateOverHTTP`, `TestLyingReadyStatusOnBlockedTicketRendersBlockedOverHTTP` |
| Dispatch issues `/fire`, surfaces the session URL; disabled when not ready | `TestDispatchDisabledForNonReadyTicketOverHTTP`, `TestDispatchFiresReadyTicketWithCorrectPayloadOverHTTP` |
| Approve merges the PR on human action only; server never merges on its own | `TestApproveMergesOnlyTheNamedPROverHTTP`, `TestApproveTicketWithNoPRReturns409OverHTTP` |
| Secrets never reach the browser / logs / committed config | `TestNoTokenShapedStringReachesClientOverHTTP` |

**Covered by unit tests elsewhere, NOT re-proven here (deliberate):**
- **Autopilot toggle** flips `.claude/autopilot.json` — unit-tested against a real checkout in
  `internal/dispatch/autopilot_test.go` (`TestSetAutopilotPreservesOtherFields`). Re-running it
  through the stub dispatcher would only exercise the stub, so it is not duplicated here.

**Remains MANUAL (out of scope for a Go HTTP e2e):**
- **UI uses only DESIGN.md tokens; a hardcoded colour fails lint** — this is a frontend
  build-time guard (`ui/scripts/check-tokens.mjs`, wired into `npm run lint`, enforced by CI's
  Node job), not something an HTTP suite can assert. It is covered, just in the other pipeline.
- **Browser-level e2e** (clicking Dispatch/Approve in the real embedded UI) — not built; the Go
  suite proves the API contract those buttons call. If added later, serve the built UI (copy
  `ui/dist` into `internal/webui/dist` per ticket 013) so the app, not the placeholder, is under
  test, and add Playwright to the Node CI job.

No product bugs were found while writing the suite.
