# FlightDeck — аудит состояния и план развития

**Дата:** 2026-07-27
**Метод:** полное чтение исходников, сборка, прогон всех тестов, запуск бинарника в demo-режиме и ручная проверка всех четырёх экранов в браузере, живые вызовы API.

---

## 1. Резюме

FlightDeck — качественно построенная **read-only витрина** над файловой очередью тикетов в git. Она вычисляет статусы из веток и PR, показывает канбан и живые сессии, и даёт человеку три write-действия: диспатч тикета в Claude-рутину, флип автопилота, апрув мержа.

Того, что описано как целевое видение — «дал задачу → ИИ декомпозировал → нажал старт → всё выполнилось в фоне без участия человека» — в коде нет. Отсутствует не «часть», а весь слой: декомпозиция, планировщик, пул исполнителей, модель агента со скилами.

| Оценка полноты | |
|---|---|
| Против собственного README (витрина над рутинами) | **~85%** |
| Против целевого видения (движок оркестрации) | **~25%** |

Фундамент — вывод статусов, чтение git, API, каркас UI — сделан хорошо и переиспользуется целиком. Недостающие слои (§5, пункты 5–9) — это примерно 70% объёма целевого продукта.

## 3. Что построено хорошо

Инженерное качество высокое, это не прототип.

**`internal/derive` — движок статусов.** Чистая тотальная функция без I/O и без часов. Все входы (статусы на main, состояние веток, открытые PR) предвычисляются вызывающей стороной, поэтому вся таблица правил тестируется на рукописных мапах без живого репозитория. Тикет, который врёт в frontmatter (`status: ready` при незамёрженной зависимости), всё равно вычислится как `blocked`. Хранимому статусу доверяют ровно для двух литералов — `done` и `needs-attention`. Это лучшая часть проекта.

**Дисциплина слоёв (ADR-004).** `internal/core` не импортирует ни одного внутреннего пакета — и это проверяется тестом, который парсит AST собственной директории. Ни один feature-пакет не импортирует другой; весь граф знает только `internal/app`. Именно это позволило собирать проект тикет за тикетом параллельно.

**Тесты.** Go-набор + 93 UI-теста. Есть e2e-набор (`internal/e2e`) с настоящими временными git-репозиториями, включая тест `lying_status_test.go` — проверку, что врущий файл тикета не ломает вывод статуса.

**Работа с секретами (ADR-005).** Токены в отдельной таблице SQLite; `core.Project` физически не имеет поля для токена. `GET /secrets` возвращает только флаги «установлен / не установлен», никогда значения. Есть тест, проверяющий, что ошибки dispatch не протекают токеном.

**SSE + фоновый refresher.** Доска обновляется сама. Refresher считает фингерпринт доски и раздельно различает структурные изменения и изменение только CI — ровно одно событие на тик на проект, без шторма.

**Дисциплина дизайн-токенов.** Все цвета в одном `tokens.css`; `scripts/check-tokens.mjs` в линте физически запрещает hex-литералы в компонентах. Цвет статуса — единственный семантический язык интерфейса.

## 4. Дефекты

### 4.1 Диспатч не может сработать ни в одном развёртывании — БЛОКЕР

Архитектура через Claude-рутины корректна и осознанна: рутина создаётся в Claude, FlightDeck дёргает её триггер, дальше она работает автономно. Проблема не в подходе, а в двух вещах.

**(а) URL захардкожен в нерабочую заглушку, и его некуда положить.**

```go
// internal/dispatch/dispatch.go:32
const defaultRoutineBaseURL = "https://routines.claude.local"
```

Комментарий рядом обещает, что composition root переопределит это. Он не переопределяет: `WithRoutineBaseURL` вызывается **только в тестах** (`fire_test.go`, `merge_test.go`). В продакшн-пути `gitHubDispatcherFactory.Dispatcher` создаёт клиент как `dispatch.New(sec.RoutineToken, sec.GitHubToken)` — без опций.

Положить URL некуда физически:
- нет колонки в схеме `projects` (`internal/registry/migrations.go`)
- нет поля в `core.Project`
- нет поля в `CreateProjectRequest`
- нет поля в форме `RegisterProjectDialog.tsx`
- нет ENV-переменной

Живая проверка на demo-проекте:

```
POST /api/projects/demo/dispatch  {"ticket_id":5}
→ 502
{"error":"dispatch: fire failed: requesting https://routines.claude.local/fire:
  dial tcp: lookup routines.claude.local: no such host"}
```

**(б) Контракт не совпадает с реальным API триггеров.**

FlightDeck реализует собственный контракт: `POST <base>/fire` с телом `{"ticket_id": N}` и ответом `{"session_url": "..."}`.

Реальный API рутин Claude:

```
POST https://api.claude.ai/api/v1/code/triggers/{trigger_id}/run
```

То есть рутина адресуется **идентификатором триггера**, а не базовым URL, тело запроса опциональное, и поле с URL сессии в ответе называется иначе. Значит нужно не просто «сделать base URL настраиваемым», а:

1. хранить per-project `trigger_id` (плюс токен claude.ai — уже есть как `routine_token`);
2. собирать URL как `/v1/code/triggers/{trigger_id}/run`;
3. передавать `ticket_id` в теле в том виде, который ожидает промпт самой рутины;
4. смапить поле ответа на `session_url` — **точную форму ответа нужно подтвердить одним живым вызовом реального триггера**, по коду это восстановить нельзя.

Альтернатива, если рутины решено заменить: интерфейс `core.Dispatcher` уже изолирует эту логику — заменяется одна реализация `internal/dispatch`, остальной код не трогается. Архитектурно точка замены выбрана правильно.

### 4.2 Проект не собирается из чистого чекаута

`go.sum` содержал 12 строк вместо 53 — отсутствовали записи для `chi` и `modernc.org/sqlite`. `go build ./...` падал. Починено через `go mod tidy` в ходе аудита; **изменённый `go.sum` нужно закоммитить**.

### 4.3 Каталог `docs/` отсутствует целиком

README ссылается на `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/DESIGN.md`, `docs/decisions/ADR-001…005`, `docs/images/fleet.png`, `docs/images/board.png` — ничего из этого не существует. Скриншоты в README битые.

При этом **48 файлов исходников** ссылаются на эти документы в комментариях:

| Документ | Ссылок |
|---|---|
| `docs/DESIGN.md` | 29 |
| `docs/ARCHITECTURE.md` | 15 |
| `docs/tickets/` | 12 |
| `docs/tickets/README.md` | 7 |
| `docs/PRD.md` | 5 |
| `docs/decisions/` | 2 |

Отдельная ирония: FlightDeck читает `docs/tickets/` чужих проектов, но у самого его нет — на себе продукт запустить нельзя.

### 4.4 Потолок по rate-limit GitHub

`OpenPRs` делает `1 + N` запросов: один список PR плюс проверка CI на каждый открытый PR (`internal/source/github/github.go`). Кэша, ETag и условных запросов нет — по требованию ADR-001 ничего не кэшируется.

Refresher опрашивает каждые 5 секунд (`FLIGHTDECK_REFRESH_INTERVAL` по умолчанию `5s`):

```
проект с 5 открытыми PR = 6 запросов × 720 опросов/час = 4 320 запросов/час
лимит GitHub для аутентифицированного клиента = 5 000/час
```

**Одного проекта достаточно, чтобы упереться в лимит.** Обработки `X-RateLimit-*` и `Retry-After` нет — при исчерпании лимита GitHub-источник просто деградирует в «PR не видны».

### 4.5 Прочее

- **Токены в SQLite открытым текстом.** Разделены по таблицам, не логируются, не отдаются в браузер — но не зашифрованы. Для self-hosted v1 приемлемо, но должно быть заявлено явно.
- **`session_url` теряется при рестарте.** `dispatchSessionStore` — in-memory (`internal/api/sessions.go`). После перезапуска сервера ссылки на живые сессии исчезают навсегда.
- **Мусор в бинарнике.** В `internal/webui/dist/assets/` накопилось 5 версий `index-*.js` и 5 версий `index-*.css` — `cp -r ui/dist/. internal/webui/dist/` из README никогда не чистит каталог, всё вкомпилировано в бинарник.
- **`go test ./...` цепляет `ui/node_modules/flatted/golang/pkg/flatted`** — постороний Go-пакет внутри node_modules попадает в сборку.

## 5. Разрыв с целевым видением

### 5.1 «Даю задачу, декомпозируем на тикеты через ИИ» — **0%**

Интеграции с LLM нет вообще. Весь `go.mod` — это `chi` + `modernc.org/sqlite`, две прямые зависимости. Ни Anthropic SDK, ни любого другого клиента.

Более того, **тикеты нельзя создать даже вручную** — в API нет `POST .../tickets`. Тикеты появляются исключительно как файлы `docs/tickets/NNN-*.md`, положенные в репозиторий кем-то извне.

### 5.2 «Нажал старт → всё выполняется в фоне» — **0%**

Диспатч — строго один тикет за один клик человека. Это не упущение, а зафиксированный принцип: *«The dashboard dispatches and merges only on explicit human action. No auto-anything on the server»*. Принцип закреплён в комментариях, в `internal/app/refresh.go` и в тесте `TestFireAndApproveMergeAreSeparateCodePaths`.

Автопилот — не оркестратор. Это булево поле, которое пишется в `.claude/autopilot.json` **внутри целевого репозитория**. Сам цикл живёт в рутине, не в FlightDeck. FlightDeck его только включает и выключает.

### 5.3 «Полностью оркестрируемая команда агентов» — **0%**

Нет очереди, планировщика, пула воркеров, лимита параллелизма, ретраев, разрешения конфликтов между агентами, приоритетов. Граф зависимостей вычисляется (`depends` → `blocked`/`ready`), но никто по нему не идёт — он только раскрашивает карточки.

### 5.4 «Каждый этап трекаемый» — **~30%**

| Есть | Нет |
|---|---|
| Производный статус | Логи агента |
| Имя ветки | Потреблённые токены / стоимость |
| Номер и URL PR | Таймлайн переходов |
| Состояние CI | Дифф / артефакты |
| Время последнего коммита в ветке | История статусов |
| `session_url` (до рестарта) | Метрики: время на тикет, доля переделок |

Экран Agents — одна строка на тикет: проект, тикет, ветка, «2m ago». «Последняя активность» вычисляется как время tip-коммита ветки — честно, но грубо: агент, который думает 20 минут не коммитя, выглядит неактивным.

### 5.5 «Добавлять агентам скилы, уточнения» — **0%**

Нет модели агента, промптов, системы скилов, конфигурации. Слово «agent» в коде — это только DTO `AgentSession` из семи строковых полей. Поле `role` тикета (`designer|frontend|backend|qa|dev`) — просто строка из frontmatter, которая нигде ни на что не влияет: не выбирает исполнителя, не подставляет промпт, не ограничивает инструменты.

## 6. Оценка UI

### Что хорошо

Дисциплина токенов образцовая (см. §3). Фокус-стили, `prefers-reduced-motion`, ARIA-атрибуты, `role="switch"` на автопилоте, клавиатурная доступность карточек — всё на месте. Тёмная палитра аккуратная, статусные цвета читаемые.

### Что требует переделки

**Экраны выглядят пустыми.** На Fleet одна карточка занимает ~15% ширины, остальные 85% — чёрный прямоугольник. На Agents — одна строка высотой 40px и ~800px пустоты под ней. Это воспринимается не как минимализм, а как незавершённость.

**Нет плотности информации.** Для «дашборда» нечего смотреть: ни прогресса по проекту, ни сводки по флоту, ни таймлайна, ни трендов, ни ленты активности, ни метрик.

**Дефект вёрстки доски.** Брейкпоинт `board: 1280px` отключает `overflow-x-auto` на полосе колонок (`ui/src/pages/Board.tsx`), но шесть колонок по 300px + гэпы требуют ~1880px. Измерено в браузере:

```
контейнер полосы: clientWidth 1632px
контент:          scrollWidth 1880px
computed:         overflow-x: visible
```

В диапазоне ~1280–1900px колонка «Done» уезжает за край, и вместо полосы колонок горизонтально скроллится **вся область `main` вместе с заголовком страницы**. Колонка достижима, но ценой уезжающего заголовка.

**Прочее:**
- Доска не показывает имя проекта — заголовок «Board» и слаг мелким моноширинным шрифтом. Хлебных крошек нет.
- Нет поиска, фильтров и сортировки — ни по роли, ни по статусу, ни по проекту.
- Кнопка Dispatch всегда видна, в том числе на тикете `in_review`, просто задизейблена — без объяснения причины.
- Нет глобального индикатора состояния SSE-соединения: если поток отвалился, экран молча замирает.
- Ошибки автопилота выводятся текстом внутри карточки и ломают её вёрстку.

## 8. Итог

Что построено — построено правильно: разделение слоёв, чистый движок вывода статусов, честная работа с секретами, живая тестовая база. Ошибок проектирования здесь нет.

Но между «панелью, которая показывает, что происходит» и «системой, которая заставляет это происходить» лежит весь этап 1–3. Точка подмены выбрана верно — интерфейс `core.Dispatcher` изолирует способ запуска, поэтому замена или расширение механизма рутин локальна. Всё остальное придётся дописывать с нуля.
